坐标系：最容易埋雷的地方

同一组数字，在不同坐标系里含义完全不同。本环境有两处已实测锁定的帧语义：

量坐标系怎么验证的（本机 CPU 实测）
自由关节 qvel[0:3]世界系线速度设 qvel[0]=0.5 → x 前进 1 mm、姿态不动
自由关节 qvel[3:6]机体系角速度躯干 yaw 90° 后设 qvel[4]=0.5，陀螺仪读 (0,0.5,0) 而非换轴后的 (0.5,0,0)

为什么较真：观测的 base_ang_vel、奖励的速度跟踪、摔倒判定的 重力投影，各自选了不同的坐标系——是设计使然，不是随手写的。你以后写 任何新的观测/奖励项，第一件事是问"这个向量在哪个系"。混用坐标系是隐性 bug： 代码不报错、训练能跑，只是策略学得莫名其妙。

动作：不是力矩，是"站姿 ± 0.5 弧度"

# microduck_brax_env.py · step()
act = jp.clip(action, -1.0, 1.0)          # 网络输出裁剪到 [-1,1]
target = self._ctrl0 + ACTION_SCALE * act  # STAND 站姿 ± 0.5 rad 的目标角
# 之后 10 个物理步里，kp=50 的位置伺服追这个目标角

三个设计决定，各有理由：裁剪防止网络输出离谱值；相对站姿偏移 让"动作 = 0"就是站好（网络从站姿开始探索，而不是从随机姿势）；位置伺服 而非力矩是 XL330 舵机的真实工作方式——真机也是发目标角。

零填充的槽：为未来留的插座

命令块的 13 维里只有 vx 在用，其余 10 维恒为零但永远保留。这来自 官方家族契约：所有策略共享同一个观测布局，将来加"抬头/蹲下"等技能时，新任务 直接把数填进这些槽，老策略可以在运行时热插拔替换。删槽 = 掐断家族的 兼容性，所以它是 CPU 测试锁定的契约之一（test_step_finite_and_command_block_padded）。

本课的动手赢面（3 分钟）：解剖一只真实的观测 
JAX_PLATFORMS=cpu python3 - <<'EOF'
from microduck_brax_env import MicroduckWalkEnv
import jax, numpy as np
env = MicroduckWalkEnv()
obs = np.asarray(env.reset(jax.random.PRNGKey(0)).obs)
for name, a, b in [("joint_pos",0,14),("joint_vel",14,28),
                   ("base_ang_vel",28,31),("proj_grav",31,34),
                   ("last_action",34,48),("command",48,61)]:
    print(f"{name:12s} obs[{a:2d}:{b:2d}] = {np.round(obs[a:b],3)}")
EOF

自检三个数：proj_grav 应接近 (0,0,−1)； command 第一位是 0~0.6 的随机速度、其余为零； joint_pos 是 ±0.03 内的小噪声。对上了，说明你正在读一只 站在起跑线上的鸭子的大脑输入。
